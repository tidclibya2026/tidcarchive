# استلام تهيئة الشبكة الداخلية — TIDC

هذا المستند موجه لمسؤول تقنية المعلومات في المركز، ويعتمد بيانات واجهة الخادم التي قُدمت في صورة إعدادات الشبكة بتاريخ 20 أغسطس 2026. لا يغير هذا المستند إعدادات Windows أو DNS تلقائياً؛ يجب تنفيذ الخطوات على الخادم من قبل مسؤول مخول وبعد التحقق من عدم وجود تعارض مع سياسة الشبكة.

قبل تطبيق الخطوات، يتحقق المسؤول من إصدار Windows. تعمل حزمة `C:\Archiving` الحالية مع Docker Desktop على Windows 10/11 المدعومين، ولا تستخدم Docker Desktop على Windows Server. توضح وثيقة `docs/برامج_التنصيب_والدعم_عن_بعد_TIDC.md` البرامج المطلوبة ومسار الدعم الآمن بين ليبيا ومصر.

## بيانات الخادم المعتمدة

| البند | القيمة |
|---|---|
| عنوان خادم TIDC | `192.168.1.2` |
| قناع الشبكة | `255.255.255.0` (`/24`) |
| البوابة الافتراضية | `192.168.1.200` |
| خادم DNS الحالي | `192.168.1.2` |
| شبكة أجهزة المركز المرصودة | `192.168.1.0/24` |
| اسم الوصول الداخلي | `tidc.ly` |
| منفذ التطبيق الداخلي | `8443/TCP` عبر HTTPS |

> القيمة `225.225.225.0` في ملف Excel السابق غير صالحة كقناع IPv4. تعتمد هذه الخطة القيمة الصحيحة الظاهرة في إعدادات واجهة الخادم: `255.255.255.0`.

## خطوة DNS الداخلية

على مسؤول DNS إنشاء سجل داخلي باسم `tidc.ly` يشير إلى `192.168.1.2`. إذا كان خادم DNS الحالي يدير منطقة داخلية باسم `ly`، ينشأ سجل `A` بالاسم `tidc`. وإذا كانت المنطقة `ly` غير موجودة داخلياً أو تتعارض مع سياسة النطاقات، يوقف المسؤول الإعداد ويعتمد اسماً داخلياً مكافئاً وفق سياسة المركز قبل تشغيل التنصيب؛ لا تستخدم ملف `hosts` على أجهزة الموظفين كحل تشغيلي دائم.

بعد إنشاء السجل، ينفذ الاختبار التالي من جهاز عميل داخل المركز:

```powershell
Resolve-DnsName tidc.ly
Test-NetConnection tidc.ly -Port 8443
```

ينبغي أن يشير الحل إلى عنوان الخادم أعلاه. لا يعني نجاح DNS أن النظام شغّال؛ يثبت تشغيل الحاويات بتقرير `Test-TIDC-Installation.ps1 -WriteReport` بعد التنصيب.

## قاعدة جدار الحماية

يسمح الخادم بمدخل واحد فقط للمستخدمين: HTTPS على المنفذ 8443 من شبكة المركز `192.168.1.0/24`. لا تفتح منافذ MySQL أو MinIO أو OCR أو ClamAV. في وضع `internal` يربط ملف الحاويات منفذ HTTP 8080 بعنوان `127.0.0.1` فقط؛ ولذلك لا يجب إضافته إلى قاعدة الجدار الناري.

يمكن لمسؤول Windows المخول إنشاء القاعدة التالية بعد التأكد من عدم وجود قاعدة مؤسسة مماثلة:

```powershell
New-NetFirewallRule -DisplayName "TIDC HTTPS – Internal LAN" `
  -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8443 `
  -RemoteAddress 192.168.1.0/24 -Profile Domain,Private
```

بعدها، يتحقق من عدم وجود قاعدة أوسع تكشف المنافذ الداخلية، ثم يشغل اختبار الحزمة. لا تستخدم نمط `public` ولا تفتح 80 أو 443 على الإنترنت لهذه المرحلة.

## ترتيب الاستلام

| الترتيب | الإجراء | الدليل المطلوب |
|---|---|---|
| 1 | تأكيد ثبات عنوان `192.168.1.2` أو حجز DHCP له. | لقطة/سجل حجز من مسؤول الشبكة. |
| 2 | إضافة DNS داخلي لـ `tidc.ly`. | نتيجة `Resolve-DnsName`. |
| 3 | تطبيق قاعدة 8443 من الشبكة الداخلية فقط. | نتيجة `Test-NetConnection`. |
| 4 | تشغيل `Install-TIDC.cmd` واختيار `internal`. | مخرجات التنصيب. |
| 5 | تشغيل `Test-TIDC-Installation.ps1 -WriteReport`. | تقرير محفوظ من دون أسرار. |
| 6 | تصدير شهادة Caddy الداخلية وتثبيتها على أجهزة المستخدمين المخولة. | فتح `https://tidc.ly:8443` دون تحذير شهادة. |

## ملاحظة أمنية

لا توزع ملف `ops\local-windows\.env`؛ فهو يتضمن مفاتيح التشفير وبيانات خدمات النظام. لا يعد عنوان IP وحده آلية صلاحية؛ تبقى حسابات المستخدمين والصلاحيات المؤسسية هي طبقة التحكم داخل التطبيق.
